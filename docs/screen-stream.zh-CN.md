# 画面流（USB 摄像头）

基于 CardenzaHAL 的固件可以把自己的屏幕作为无损画面流交给电脑（`usb/camera.h`），专为录制和直播教程而做：网页把它和设备的 USB 音频一起显示、录制；桌面程序可以把它变成 OBS 用的虚拟摄像头。本文是读取端要实现的协议；参考实现是 [`tools/web/screen-stream.js`](../tools/web/screen-stream.js)（浏览器，或只用解码部分时的 Node），[`tools/web/screen-stream-demo.html`](../tools/web/screen-stream-demo.html) 是可以直接运行的演示。

像素完全准确：每一帧都是固件提交时的屏幕，RGB565，全程没有有损环节。只发送和上一帧相比变化的部分，按矩形发送，原样或使用一种简单的游程编码（在 groovebox 的界面上只需原始字节的 30-45 %）。只有画面变了、并且电脑已经读完上一帧时才发下一帧：电脑比固件慢时收到的帧更少，但每一帧都包含自上一帧以来的全部变化（不会积压，也不会画面撕裂）。画面不动时什么也不发。

## 找到它

任何 203 设备（USB 厂商 ID `0x0203`），只要固件打开了摄像头（`CardenzaHAL::USB::Camera::Enable(true)` 或 `USB::Config::camera`；Kconfig `CONFIG_CARDENZA_HAL_USB_CAMERA`）。画面流在名为 **"Cardenza WebUSB"** 的接口上：类 `0xFF`（厂商自定义），子类 0，协议 0，有一个 **bulk IN 端点**（64 字节包，全速）。没有摄像头时这个接口没有端点（只承载系统通道，见 `docs/usb-dev.md`）。它的接口号取决于固件的其他 USB 类：按类和端点找，不要写死接口号。

- **浏览器（WebUSB，Chrome 和 Edge）：** 先 `navigator.usb.requestDevice({filters: [{vendorId: 0x0203}]})` 一次（选择框），之后用 `getDevices()`；`open()`，未选配置时 `selectConfiguration(1)`，对带 bulk IN 端点的厂商接口 `claimInterface(n)`。下面的控制请求是 `{requestType: 'vendor', recipient: 'interface', request, value, index: n}`。页面必须是安全来源（https 或 localhost）。
- **macOS 和 Linux（libusb）：** `libusb_open_device_with_vid_pid(ctx, 0x0203, pid)`，或遍历设备找厂商 `0x0203`；在 `libusb_get_active_config_descriptor` 里按上面的方法找接口；`libusb_claim_interface`。macOS：厂商接口没有驱动占用，程序直接认领即可（不需要内核扩展或授权）。Linux：用户需要设备节点的权限（为厂商 `0203` 加 udev 规则，例如 `SUBSYSTEM=="usb", ATTR{idVendor}=="0203", MODE="0660", TAG+="uaccess"`）。
- **Windows（WinUSB）：** 设备的 Microsoft OS 2.0 描述符让 WinUSB 自动绑定到这个接口，不用装驱动，DeviceInterfaceGUID 为 **`{3C0D4A20-0203-4C5A-B1E5-CA4DE2A0B0E1}`**：用这个 GUID 调 `SetupDiGetClassDevs`，对得到的路径 `CreateFile`，再 `WinUsb_Initialize`；控制请求用 `WinUsb_ControlTransfer`（`RequestType` 输出 `0x41`、输入 `0xC1`；`Index` 为接口号），画面流用 `WinUsb_ReadPipe`。Windows 上的 libusb 也通过同一个 WinUSB 绑定工作。

## 控制请求（端点 0）

发给该接口的厂商请求（`bmRequestType` 主机到设备 `0x41`、设备到主机 `0xC1`；`wIndex` 为接口号）：

| bRequest | 名称 | 方向 | wValue | 数据 |
| --- | --- | --- | --- | --- |
| `0x20` | START | 输出 | 第 0 位：允许使用游程编码 | 无。开始（或重新开始），第一帧是关键帧。设备没有足够内存时失败（stall；需要 130 KB PSRAM） |
| `0x21` | STOP | 输出 | 0 | 无。停止采集，不再发送 |
| `0x22` | KEYFRAME | 输出 | 0 | 无。下一帧是关键帧 |
| `0x23` | INFO | 输入 | 0 | 16 字节（见下） |
| `0x24` | STATS | 输入 | 0 | 64 字节（见下） |

读取端开始读端点后发一次 START；丢了东西（序号不连续、帧损坏、中途加入）时发 KEYFRAME。不发 STOP 也没关系：总线复位、拔线或主机重新配置都会结束画面流；读取端 2 秒不读，设备就暂停（期间不采集；恢复读取后的第一帧是关键帧）。读取端回来后再发一次 START，会重置帧状态。

INFO：`u8 版本`（1）、`u8 格式`（1：RGB565）、`u16 宽`（240）、`u16 高`（135）、`u8 状态`（第 0 位已开始，第 1 位已暂停：读取端不读了）、`u8` 0、`u32` 下一帧的序号、`u32` 最大帧长（64852）。

STATS（设备的开销；`usb/camera.h` 的 `Stats`）：`u8 状态`（第 0 位已启用，1 端点已配置，2 已开始，3 已暂停）、3 字节 0，然后依次是 `u32`：帧数、关键帧数、矩形数、看到的固件帧数、其中被合并进后一帧的数量、已发送字节、上一帧字节数、下一帧序号、采集耗时 µs（上一次、最大：固件 Present 里的比较）、写帧耗时 µs（上一次、最大）、错误数；最后 8 字节 0。

## 画面流（bulk IN 端点）

由**帧**组成的字节流，每帧是一次 bulk 传输：设备用短包结束每一帧，帧长正好是 64 的倍数时再补一个零长度包，所以每次请求 65,536 字节的读取端（`transferIn(ep, 65536)`、`libusb_bulk_transfer`、`WinUsb_ReadPipe`）每次正好读到一帧。用更小的块读取时，把数据当字节流解析即可：每帧都写明自己的长度。所有数值都是小端序。

### 帧

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| 0 | 4 | 魔数 `43 44 5A 53`（"CDZS"） |
| 4 | 1 | 版本：1 |
| 5 | 1 | 标志：第 0 位关键帧（这一帧画满整个屏幕，不依赖之前的帧） |
| 6 | 2 | 帧头字节数：32 |
| 8 | 4 | 帧字节数：整帧，含帧头和帧尾（最多 64852） |
| 12 | 4 | 序号：已发送帧的计数，从设备当时的值开始；到 2^32 回绕 |
| 16 | 2 | 宽：240 |
| 18 | 2 | 高：135 |
| 20 | 1 | 像素格式：1 = RGB565（第 15-11 位红，10-5 绿，4-0 蓝），每像素 2 字节小端 |
| 21 | 1 | 0 |
| 22 | 2 | 本帧矩形数 |
| 24 | 4 | 本帧中最新一帧被提交时设备的时间（毫秒） |
| 28 | 2 | 合并进这一帧的固件帧数（1：没有跳过） |
| 30 | 2 | 0 |
| 32 | ... | 矩形 |
| 末尾 - 4 | 4 | 帧尾 `43 44 5A 45`（"CDZE"） |

### 矩形

16 字节的头，然后是数据，用 0 补齐到 4 字节的倍数（补齐部分不计入长度）：

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| 0 | 2 | x |
| 2 | 2 | y |
| 4 | 2 | 宽 |
| 6 | 2 | 高 |
| 8 | 1 | 编码：0 原样，1 游程编码 |
| 9 | 3 | 0 |
| 12 | 4 | 数据字节数（不含补齐） |

原样：`宽 × 高` 个像素，行从上到下，每行从左到右，每像素 2 字节。矩形互不重叠；x 和宽都是 8 的倍数。关键帧是覆盖整个屏幕的一个矩形。

### 游程编码

矩形的像素按行从上到下、每行从左到右排成一个序列，分成若干块。每块以一个 `u16` 控制字开头：高两位说明后面是什么，低 14 位是像素数 `n`（1 到 16383）：

| 高两位 | 块 | 后面跟着 |
| --- | --- | --- |
| `00` | 原样 | `n` 个像素 |
| `10` | 重复 | 一个像素，重复 `n` 次 |
| `01` | 交替 | 两个像素 A、B：然后按 A B A B ... 排满 `n` 个像素（界面里两像素一组的抖动和条纹） |
| `11` | 保留 | （读取端把整帧当作损坏） |

所有块合起来正好填满 `宽 × 高` 个像素。

### 读取步骤

1. 找到魔数，读 12 字节，检查帧字节数（32 + 4 到 64852），等整帧到齐。不是帧的数据（中途加入的读取端、之前读取端留下的半次传输）逐字节跳过，直到下一个魔数。
2. 检查版本、帧头长度、宽、高、格式和帧尾；先检查每个矩形都在屏幕内、在帧内，再开始画（损坏的帧一个像素也不画；请求关键帧）。
3. 不是关键帧的帧画在上一帧的屏幕上：第一个关键帧之前的帧跳过并请求关键帧（KEYFRAME）。序号不是上一帧加 1 说明丢了帧：照常画下去，同时请求关键帧。
4. 把矩形画进 240 × 135 的 RGB565 屏幕。转成 8 位颜色：把每个通道的高位重复到低位（`r8 = r5 << 3 | r5 >> 2`，`g8 = g6 << 2 | g6 >> 4`，`b8 = b5 << 3 | b5 >> 2`）。只按整数倍、用最近邻放大（canvas 加 `image-rendering: pixelated`），才能保证每个像素准确；240 × 135 是 16:9，1920 × 1080 的虚拟摄像头正好每个设备像素 8 × 8（1280 × 720 不是整数倍，5.33 倍）。

## 设备的开销

- 没有读取端（或摄像头关闭）：零开销。显示的提交路径只判断一个指针。
- 读取时：内存是屏幕副本 64.8 KB 和正在发送的帧 64.9 KB，都在 PSRAM，只在读取端开始后存在；一个优先级 1 的任务，栈 3.5 KB（内部 RAM）；约 1 KB 静态内部 RAM。时间：在固件的 `Present` 里，把它提交的行和副本按 16 字节一段比较（对 `PresentChanged` 是它找到的变化行和它的刷新带）；在画面流任务里，把变化的矩形写进帧（游程编码对它们只扫一遍）。
- 总线：一个 bulk IN 端点，全速（12 Mbit/s），与设备的其他类共用（音频的同步流优先）。电脑跟不上每一帧时，变化会被合并。

在录制和合成的画面上（主机测试 `tests/camera_test.cpp`，`CardenzaCameraTests` 会打印）：groovebox 页面的关键帧 8-27 KB（原样 64.8 KB）；两像素宽的播放头在音序器网格上走动约 14 KB/s；CardenzaSynth 录制的界面巡览（CardenzaSynth 的 docs/groovebox/motion：切页、切场景、动画）在每秒 33 帧时为 65-245 KB/s，是原样字节的 28-39 %；全屏噪声动画无法压缩，每帧 64.8 KB，帧率由总线决定。
