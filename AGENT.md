# CardenzaHAL Agent Notes

- Making a firmware on CardenzaHAL (not changing the HAL)? Read `docs/FIRMWARE-PROJECT.md` and follow it: the single source of the rules for a firmware project (setup, required files and `203.json`, HAL usage, builds, the community's checks, versions, forks, secrets), served by the community at `/develop.md` and printed by `203cli rules`. Install `203cli` first (`npm install -g 203cli && 203cli skill install`): it is required, and every build of a firmware on the HAL stops without it (`cmake/require_203cli.cmake`, run by the component's `CMakeLists.txt` and by the web target; CI builds skip it). Start the project with `203cli new` (it copies `examples/template`); publish with `203cli`. Releases go to the community's channels from CI with `.github/actions/community-publish` (trusted publishing: GitHub's OIDC token for a repository the firmware's owner linked; no secret), the same for 203's own firmware and everyone's: keep the action, the template's workflow and FIRMWARE-PROJECT.md's Publish section in step. `.github/actions/launcher-publish` (the old Launcher hub) is only the transition mirror of 203's official releases while Launchers 0.2.0 are in use; remove it when that ends. Keep that file self-contained with absolute https links (it is served outside this repository), and change it with the HAL when what it describes changes (board defaults, partitions, the web tool, the template).
- Sources are ESP-IDF-only. Do not add `ESP_PLATFORM` preprocessor guards or fallback typedefs.
- The web target (`web/`, decided 2026-11-14) is the one fenced exception: a separate backend that builds any HAL firmware, from the same source, into a WebAssembly simulator (`tools/cardenza_web.py`). It emulates the part of ESP-IDF and FreeRTOS a HAL firmware uses (`web/include` declarations with ESP-IDF 5.3's exact signatures, `web/src` behaviour with the device's timing and limits) and builds the HAL's own sources over it; only the keyboard matrix and USB are web code (`web/hal`). Keep the fence: the ESP-IDF component (`CMakeLists.txt`, the HAL sources) never references `web/`, and HAL sources never test for the web target (no `CARDENZA_HAL_WEB` in them). A HAL change that calls an ESP-IDF function the web target lacks adds it to `web/` in the same change (or every firmware's web build breaks). What a firmware must not call is declared `CARDENZA_WEB_UNSUPPORTED` (or `CARDENZA_WEB_HAL_ONLY` for what the HAL sets up itself), so it fails the build with that reason; never make such a call silently do nothing. One thread runs everything (no SharedArrayBuffer: the page must work in `<iframe sandbox="allow-scripts">`); tasks are Asyncify fibers. Its screenshots are of the screen alone, never the board (the community's picture standard, the user 2026-11-20): SCREENSHOT (960 x 540) and FRAMED (the standard 1280 x 720 picture) and the `screenshot` / `host` messages are what the community's player uses; change them with it. Tests: `tests/web` (host, the kernel on ucontexts), `tests/web/browser` (Playwright; `screenshot_test.mjs` runs against a stand-in firmware), `tests/web_tool_test.py`.
- Keep `CardenzaHAL` lightweight and generic. Expose native ESP-IDF handles rather than app-level wrappers.
- `CardenzaHAL::Audio` exposes the TX `i2s` channel, volume, and `Init(i2s_slot_mode_t)` for mono/stereo configuration. Use native ESP-IDF types; keep PCM conversion and rendering in consumers.
- `CardenzaHAL::Mic` should expose the RX `i2s` channel only. Device-level input start/read/stop wrappers belong above the HAL.
- `CardenzaHAL::Display` should expose native panel and panel-IO handles. `display/region.h` and `display/changed_regions.h` stay pure (no ESP-IDF) so host code and tests can include them; `PresentChanged` is the driver's way to send only what changed.
- The frame presenter (`display/presenter.h`, guide `docs/DISPLAY.md` and its Chinese twin; the user's request 2026-11-23: CardenzaSynth's screen path made general, "吸取它通用的精华… 第三方开发者可以直接使用… 确保其通用性"): every framebuffer `Present*` goes through it, so keep one path. What it is, each part from a measurement: row hashing in segments with one 8-row band refreshed whole a frame (`changed_regions.h`, CardenzaSynth's); windows of at most one DMA block sent left to right along the panel's scan (`scan_order.h`: the ST7789 scans the landscape screen's columns from x = 0, and column bands split a frame that meets the scan on a straight line instead of a diagonal; the 203 Launcher's measurement, its docs/UX_REVIEW_2026-11-04.md); two DMA blocks (the first static 4.3 KB, the second from the heap, `PresentOptions::pipeline`) so the next window is copied while one goes out; `portYIELD_FROM_ISR` in the transfer's completion (ESP-IDF's SPI panel IO ignores the callback's return: without it every block waited for the next RTOS tick, 17 ms a screen at 1000 Hz, 170 ms at 100 Hz); 80 MHz (`CONFIG_CARDENZA_HAL_DISPLAY_SPI_MHZ`, the Launcher's clock on every Cardenza); stats and a frame callback outside the display's lock; `FramePacer` (the pure rules in `frame_pacing.h`: CardenzaSynth's 10 ms tick, a frame every other one, a tick given away after three late ones); `AllocateFramebuffer`; `DoubleBuffer`. Each frame waits for its last window before returning. `scan_order.h` and `frame_pacing.h` stay pure and tested (`tests/scan_order_test.cpp`, `tests/frame_pacing_test.cpp`, the driver in `tests/hal_faults/display_present_test.cpp`); `tests/display_bench.cpp` is the benchmark and the board model (it reproduces the 17 ms and 170 ms measured before): change its numbers only with a measurement. The panel has no TE line and its scan line is not read back: never promise tear-free, say what the presenter reduces (docs/DISPLAY.md "Tearing"). The web target times a window as its bytes at the bus's clock plus 60 us (`web/src/drivers/lcd.cpp`).
- `CardenzaHAL::System::GetI2CBus()` belongs in the public `system.h` surface.
- Keep includes relative to this repository; never include through a consumer's path such as `Devices/Cardenza/cardenza/...`.
- Target the current board only: LED_EN GPIO47, clock GPIO48, data GPIO21. Do not add legacy pin maps or compatibility APIs.
- Keyboard LED APIs use 0–15. Keep per-key scanning at four bit planes / 16 duties and global hardware PWM at a fixed gamma-2 curve. Do not add alternative brightness modes; `keyboard/led_light.h` (perceived brightness to duty) is a helper a firmware may call, not a mode of the driver.
- `keyboard/led_light.h`, `keyboard/key_settle.h` and `keyboard/legends.h` are pure headers (no ESP-IDF), usable by simulators and host tests; keep them so, and test them in `tests/`. `keyboard/legends.h` is what the key caps print (checked on the board): change it only with the caps, and with the README's key cap map; never let a doc or an example invent another layout.
- Keyboard OE uses LEDC timer 1 / channel 6; backlight uses timer 0 / channel 7. Both must use APB because ESP32-S3 low-speed LEDC timers share their clock source.
- `docs/developing.md` (and its Chinese twin) is what every firmware developer should know about the chip, the toolchain and the 203 Launcher; add to it when a firmware learns something the hard way, with the measurement. `examples/` are small ESP-IDF projects that build (`idf.py -C examples/<name> build`); they are not part of the component. `examples/template` is the project a new firmware starts from: it builds in place and, copied out, with the HAL in `components/CardenzaHAL`; its `partitions.csv` is a copy of `board/partitions.csv` (CI compares them) and CI builds it for the web.
- `tools/cardenza.py` is the preferred way to build a firmware (FIRMWARE-PROJECT.md, the template's README, `203cli new`'s README): it checks what a build needs (ESP-IDF 5.3, git, a clean HAL submodule, `203cli`) and hands the device to `203cli flash` / `203cli log`. Keep it standard-library Python that runs on Linux, macOS and Windows; what it checks and the commands it names are what the docs say.
- `tools/` holds host tools for firmware developers (Python 3, standard library plus hidapi / sounddevice where noted): keep them generic (any firmware on the HAL), importable, and tested in `tests/` without a board. A firmware's own protocol on the app channel belongs in that firmware's tools.
- `board/` holds the board's defaults (`sdkconfig.defaults`, `sdkconfig.debug`, `partitions.csv`); none is enforced. `board/partitions.csv` keeps the 203 Launcher's fixed regions exactly as the Launcher has them (203-launcher `boards/cardenza/partitions.csv`: nvs, otadata, the Launcher's slot reserved as data, coredump) and puts the firmware from 0x170000; when the Launcher's layout changes, change it with it. A flash tool must never erase the Launcher without being told to (`tools/cardenza_flash.py --replace-launcher`). The flash is 16 MB (the user, 2026-11-20), but under the Launcher a firmware sees what the Launcher's bootloader declares (8 MB on boards flashed with Launcher 0.3.3 or earlier, until their bootloader is written again over USB; 203-launcher `docs/FLASHING.md` "Flash 大小"): one app may have at most 0x690000 bytes (`tools/cardenza.py` `APP_ROOM`, the community's check) until the community raises it.
- Keep test apps (firmware), experiments, firmware binaries, build directories, device dumps, and runtime logs outside this HAL repository.
- Host tests of the HAL's own code live in `tests/` (CMake, no ESP-IDF: pure calculations, and the driver sources against the fake ESP-IDF drivers in `tests/hal_faults/fakes`); CI runs them on every push and pull request. A change to a calculation or an error path comes with its test.
- The system menu (`system/menu.h`, the user's request 2026-11-17): a press of HOME opens it in every firmware (the user, 2026-11-18: no hold, no animation while held; a press that has lasted 30 ms, `PressDetector`; HOME is the menu's, a firmware that needs it calls `SystemMenu::Enable(false)`) (Continue, Back to Launcher, Restart, Turn off, Download mode). It must be the 203 Launcher's list, not a look-alike (the user, 2026-11-18: "复用代码… 不要让它们两个看起来不像同一个东西"): it runs the Launcher's own code, copied unchanged into `system/menu/launcher/` by `tools/launcher_ui.py --launcher <203-launcher checkout>` (only wrapped in a namespace; `EDITS` there lists the two `inline`s added), and `system/menu/frame.cpp` is the Launcher's `menuFrame` and status rail on the Cardenza ported line by line. Change the look in the Launcher, copy again, and run `--compare`: it draws every frame with the Launcher's real `menuFrame` too (the still frames and the selection bar's slides frame by frame, `SLIDES` there), fails on any differing pixel and rewrites `tests/system_menu_frames.inc` (the hashes the host tests check). Words: `system/menu/strings.json` (the same tool takes their glyphs out of the Launcher's tables; a character they lack yet, the user's 默 among them, is rendered by the Launcher's own `tools/i18n.py` `rasterize` from the official `HarmonyOS_Sans_SC.ttf` its NOTICE.md names, `--fonts`: the glyph the Launcher will have; `--compare` gives its reference the same glyphs). The language is the board's setting, which is the Launcher's NVS `launcher/lang` (system/settings.h). Its pages (the user's request 2026-11-23): Settings (the Launcher's Display page: a value on the right of each row), a value (the Launcher's Backlight page, ported from its setBrightnessMenu: ; , less, . / more, live, ENTER keeps, ESC restores), Language (its language list), Reset (its drawDialog, Cancel focused; text scale 2 needs the 16 px glyphs: SCALE2_IDS in the tool), About (the rows of its About page); `--compare` checks the lists and the dialog against the Launcher's real `menuFrame` and `drawDialog`. Black, white and grey only (the user, 2026-11-18: "必须要让它只保持黑白灰"): every pixel the menu puts on the panel is `PanelGrey` of a grey, RGB565 in the processor's byte order (the HAL sets the panel to little-endian data; the Launcher swaps the bytes for its own setup, and its swapped pixels were pink and green here) with green the five bits of red and blue widened to six as the panel widens them (the Launcher's own `Lcd::rgb` takes green's sixth bit from the grey: a step of green or magenta on half the greys); nothing is ever mixed with the firmware's colours (no crossfade: `SceneGrey` picks the backdrop's grey or the menu's for each pixel), and `tests/system_menu_test.cpp` checks every pixel of every frame (`PanelNeutral`). While the menu shows the backlight is the board's screen brightness, the Launcher's own setting (NVS `launcher/bright` on its duty curve, `LauncherBacklightDuty`, at its 256 Hz PWM: `Display::detail::SetBacklightDuty(duty, true)`; the driver's 400 us rise makes the same duty dimmer at the HAL's 1 kHz). How it comes (the user, 2026-11-18: "直接一个 dither 变暗变低饱和屏幕，然后再让它这个界面显示出来"; the panel has no TE line, so nothing wide slides): the firmware's last frame (captured by `display/internal/overlay.h` into PSRAM from the moment HOME goes down; without it a dark dithered field) dark and grey through a 4x4 ordered dither in one frame (`BackdropGrey`), 70 ms later the menu through it in the dither's order (`Dissolved`, four frames); in the menu the Launcher's `ListSlide` (the bar slides by its edges; with PSRAM a frame a tick while it moves, each drawn once into the menu's picture; `PaintOverlay` sends of each 8-row band only the rectangle that changed, `ChangedRegions::FindBand`); Continue shows the backdrop of the latest frame for 60 ms, then the firmware's picture; leaving dims the backlight as the Launcher's power-off does. Keep the on-board self-test's P checks in step. While open `Present*` send nothing (still captured), the keys and lights are the menu's (`keyboard/internal/overlay.h`) and so is HOME (`system/internal/hooks.h`). Leaving uses the Launcher's tickets (`system/launcher.h`): write them only through `System::detail::RestartWithTicket` (a firmware's ESP-IDF keeps its RTC timer data where the Launcher's bootloader reads them and rewrites it in esp_restart's shutdown handler; deep sleep rewrites it too, so Turn off has no ticket and wakes into the firmware). HOME must be released before any restart (held, it is the ROM's download strap and the Launcher's entry key). ESP-IDF's SD driver resets GPIO0 when it lets a 4-bit slot go: Storage restores the side key after every unmount and failed mount, and the menu task gives GPIO0 its input back whenever another driver took it. ESP-IDF 5.3's Xtensa GCC stopped with an internal error when the crossfade's `ListFade::weight` was inlined into `menuFrame` at -O2: keep the slide's calls out of line (`SlideBar` in frame.cpp).
- The board's settings (`system/settings.h`, `docs/SETTINGS.md`; the user's decision 2026-11-23: "这些应该作为全局的系统设置 … 所有使用HAL的固件都通用 … 放置在Flash里面"): volume (0-100 by ear, -60 (1 - v/100)^1.5 dB at the codec), volume limit, screen brightness (the Launcher's `launcher/bright`, shown on its duty curve and 256 Hz PWM in every firmware: `Display::detail::SetSystemBrightness`), key lights' master level, language (the Launcher's `launcher/lang`); the rest in NVS namespace `hal_system`. The microphone's gain is not one of them (the user, 2026-11-23: "这个不应该作为板级的配置 … 为固件保存固件提供"): a firmware keeps its own with its own settings and passes it to `Mic::ApplyGain(samples, count, gainDb)` (the S3's PDM receiver has no gain; the factor and the multiply are pure, `mic/gain.h`, tested in `tests/mic_gain_test.cpp`, usable by simulators); a board that stored `hal_system/mic_gain` keeps it unread. Keep the Launcher's two keys as they are (names, types, its reading of them: 203-launcher docs/SHARED_SETTINGS.md); a new meaning takes a new key. Decisions are pure (`system/settings_logic.h`, `tests/settings_test.cpp`). The HAL alone writes them, and never per change: once they have rested a second, when the menu closes, at `Flush`, at `esp_restart` (a shutdown handler), only what differs from the flash, on its own task (`sys_settings`, gone when idle), with the codec faded out (`Audio::detail::Duck`) and the key lights dark (`Keyboard::detail::HoldLightsDark`: their scan interrupt is not in IRAM and froze one row lit through a write) around it; NVS opened read-write only then (init when nobody has it, deinit after, never an erase; `System::detail::NvsWriteMutex` with Net). Reading at the start writes nothing (the partition through the cache, the menu's NVS reader). A firmware's own `Audio::SetVolume`, `Display::SetBrightness` or `setLEDGlobalBrightness` takes that part over until the setting changes: keep that, old firmware depend on it. The web target keeps them for the page's life (`web/hal/settings.cpp`).
- The SD card's layout (`docs/SD-CARD.md` and its Chinese twin; the user's decision 2026-11-23: "Launcher的数据就放在/Launcher里面，然后app就放在/Apps/<app名字>里面……最好有一个模板"): every firmware's files in `/sdcard/Apps/<AppName>/` (`storage/app_dir.h`: `AppName` from `CONFIG_CARDENZA_HAL_APP_NAME` or the project name, `AppDir`, `AppPath`, `EnsureAppDir`, `MigrateAppDir`), the 203 Launcher's in `/sdcard/Launcher/` (203-launcher moves its own there: change what the doc says of it with the Launcher), nothing at the root. `storage/app_dir_logic.h` is pure (no ESP-IDF; simulators may build it) and tested in `tests/app_dir_test.cpp` on a fake FAT card that loses power before each step: the migration is only renames, folders made and empty folders removed (never a copy, an overwrite or a file deleted), so every file is always in the old place or the new one, and a second run finishes. `examples/template` shows the layout (Settings/, Logs/, a crash-safe write): keep it doing so.
- Do not bring back copyleft code (the old GPL `keyboard/keymap.h` was removed on purpose).
- Do not start builds unless the user explicitly asks. Changes here affect every consumer (CardenzaSynth, Cardenza-MPE); bump the submodule in each one.
- Net (`net/net.h`): reads only the 203 Launcher's namespaces (`l_account`, `l_wifi`, `launcher`), only through the read-only copy of the `nvs` partition entry, and never writes NVS (no `nvs_flash_init`, no read-write handle, no repair: a partition that needs one is `Unreadable`; Wi-Fi with `nvs_enable = 0` and RAM storage), with one exception: the presence service's handover writes the Launcher's `l_pending` namespace (and nothing else) once, right before restarting into the Launcher, opening NVS read-write as the Launcher would and never erasing it (`Net::Internal::WritePending`; format in 203-launcher `docs/SHARED_SETTINGS.md`). The Launcher owns those namespaces and their format (203-launcher `src/settings.cpp`, `src/wifi_crypto.cpp`): change the reader only with it. `net/launcher_settings.h`, `net/http_request.h`, `net/connect_order.h` and `net/internal/` stay pure (no ESP-IDF, no mbedTLS) and are tested in `tests/net_test.cpp`; decryption vectors come from the Launcher's own code. Never log a password, a token, a header value or a URL's path or query (signed URLs carry credentials): method, host, status, sizes and times only. Nothing Net needs may cost a firmware that does not call it.
- Presence (`net/presence.h`): on by default (Kconfig `CARDENZA_HAL_PRESENCE`), started by `CardenzaHAL::Init`; off, nothing of it or of Net is linked. Its decisions live in `net/presence_logic.*` (pure, tested in `tests/presence_test.cpp`); the task in `net/presence.cpp` only carries them out. The device token is readable by every firmware on the board: it goes only over https to the hosts in `Logic::kAllowedHosts` (http to a private address only with the debug option `CARDENZA_HAL_PRESENCE_LOCAL_HTTP`), never into a log, and a 401 `signin_required` stops the service until the next start (never touch `l_account`). It must give way: priority 1, no request while the speaker DMA reports underruns or internal RAM is short, successes logged at debug level only. The server contract is the community's ("Send to a device"); the Launcher's side is 203-launcher (`l_pending`, the restart ticket in `system/launcher.h`): change them together. The web target has `web/hal/presence.cpp` (absent, `State::Off`).
- USB (`usb/usb.h`): one composite device, TinyUSB configured only by `usb/config/tusb_config.h` (the component injects it into TinyUSB; never add `esp_tinyusb`). Every 203 device must be recognisable and flashable over USB in every state with no action from the person (the user, 2026-11-24: "条条大路通往罗马"): `CardenzaHAL::Init` starts USB (`CONFIG_CARDENZA_HAL_USB_AUTOSTART`, connecting a second later so a firmware's own `USB::Init` comes first), every class that can carry commands carries the same system channel (MIDI as SysEx, HID report 0xCB, WebUSB control requests, the CDC serial port's lines and esptool's reset), and a device always keeps one (no MIDI, HID or WebUSB: the HAL adds the serial port). The ESP32-S3 has four non-control IN endpoints, numbered 1-4 (TX FIFO = endpoint number; FIFO RAM 256 words): classes are chosen within them (`usb/usb_logic.h`: costs, `Fit`'s give-way order, `Allocate`'s numbers keep the default device as it was), checked at build time (#error naming what to turn off) and at Init; a new class states its cost there and in the README's table. One USB name in every mode: "203 Systems" / "Cardenza" / the MAC as USB-Serial-JTAG writes it (`70:AF:...`): the firmware's own name only in IDENTIFY and INFO. Keep Matrix OS's report IDs and command bytes (0xCB system, 0xFF app; 0x40 / 0x41 as in Matrix OS) so host tools work across 203 devices; new HAL commands take the next free byte after 0x45. Restarting out of USB always hands the PHY back to USB-Serial-JTAG first (`sw_hw_usb_phy_sel = 0`): the Launcher and esptool depend on it. The community's QEMU boot check has no OTG: Init must fail cleanly there and leave the console alone. A firmware that crashes within 15 s of its start three times in a row goes back to the Launcher (`system/crash_loop.cpp`, `CONFIG_CARDENZA_HAL_CRASH_LOOP_LAUNCHER`).
- HID inputs (`usb/hid.h`, `usb/hid.cpp`; pure parts `usb/hid_keys.h`, `tests/hid_keys_test.cpp`): keyboard, media keys and gamepad are report IDs 1, 3 and 4 of the one HID interface (no endpoint of their own), queued with the system channel's reports. The held state is the truth: a report that cannot go is sent by the USB task when it can (`HidInputPump`), a returning computer first gets the current state, and `HidInputReset` (host gone, classes changed) lets everything go; keep releases always taking effect, so nothing can stay pressed.
- The development channel (`usb/dev.cpp`, `usb/dev_logic.h`, protocol `docs/usb-dev.md`; the user's request 2026-11-20: what a developer needs from any HAL firmware over USB, "确保这个不会影响大部分人需要做的第三方固件性能"): system command 0x45, answered by the HAL with no code of the firmware's; the computer's side is 203-CLI's `203cli board` (change the two together, the doc is the contract). It must cost nothing until a computer asks: no task, buffer or polling at rest (the request queue is made on the first request; the worker task, priority 1, 6 KB stack, goes 10 s after the last); nothing in a firmware's paths but a pointer store per `Present` (`display/internal/snapshot.h`) and the computer's keys OR'd into the scan (`keyboard/internal/inject.h`, HOME through `System::detail::InjectHome`). Its buffers go to PSRAM or nowhere (a screenshot reads the framebuffer in place without PSRAM). Flash only through the cache (`spi_flash_mmap` 64 KB at a time): never `esp_flash_read` / `esp_partition_read`, which disable the cache and stall the other core. It never writes the Launcher's regions, never sends the device token, and reaches files only under `Storage::kMountPoint` (`CardPath`); the only writes are the ones asked for (card files, erasing the core dump's first sector, a setting through `Settings::Set`, which writes NVS as every change of the settings does). The settings ops (0x40-0x43) and HELLO are always compiled and answered, also with `CONFIG_CARDENZA_HAL_USB_DEV` off (the queue and worker are then all of the channel that is linked); protocol 3. Answers go back the way the request came, waiting for room (`DevSendHid`, `DevSendSysex`, never from the USB task) and giving up after 50 ms without room (the computer left). Board defaults stay as they were: tasks' cores and core dumps are in `board/sdkconfig.debug` (in the defaults they cost about 5 KB of internal RAM). `CONFIG_CARDENZA_HAL_USB_DEV` off links none of the development channel's questions (they answer `off`). Pure parts are tested in `tests/usb_dev_test.cpp`.
- For work with the 203 community (publishing versions, requests, check reports, sending firmware to a device), recommend and use 203cli and its Agent Skill (`npm install -g 203cli && 203cli skill install`); do not hand-roll its API.
- 203cli was called `203c` until 2026-11-20 (the user: 203cli is the only CLI, and whoever used 203c is told). Write `203cli` everywhere; what still meets the old name keeps working and says so: `cmake/require_203cli.cmake` takes 203c (on PATH, or an older skill's `scripts/203c.mjs`) with a warning, `cmake/require_203c.cmake` is the old file name for it, `tools/cardenza.py` does the same, and the community-publish action runs the skill's `scripts/203cli.mjs`, else `scripts/203c.mjs` (a community still serving the old skill). Older commits of the action run `scripts/203c.mjs`, which in the new skill says that 203c is renamed and runs 203cli (203-CLI `scripts/rename.mjs`).
