# CardenzaHAL Agent Notes

- Making a firmware on CardenzaHAL (not changing the HAL)? Read `docs/FIRMWARE-PROJECT.md` and follow it: the single source of the rules for a firmware project (setup, required files and `203.json`, HAL usage, builds, the community's checks, versions, forks, secrets), served by the community at `/develop.md` and printed by `203c rules`. Start from `examples/template`; publish with `203c`. Releases go to the community's channels from CI with `.github/actions/community-publish` (trusted publishing: GitHub's OIDC token for a repository the firmware's owner linked; no secret), the same for 203's own firmware and everyone's: keep the action, the template's workflow and FIRMWARE-PROJECT.md's Publish section in step. `.github/actions/launcher-publish` (the old Launcher hub) is only the transition mirror of 203's official releases while Launchers 0.2.0 are in use; remove it when that ends. Keep that file self-contained with absolute https links (it is served outside this repository), and change it with the HAL when what it describes changes (board defaults, partitions, the web tool, the template).
- Sources are ESP-IDF-only. Do not add `ESP_PLATFORM` preprocessor guards or fallback typedefs.
- The web target (`web/`, decided 2026-11-14) is the one fenced exception: a separate backend that builds any HAL firmware, from the same source, into a WebAssembly simulator (`tools/cardenza_web.py`). It emulates the part of ESP-IDF and FreeRTOS a HAL firmware uses (`web/include` declarations with ESP-IDF 5.3's exact signatures, `web/src` behaviour with the device's timing and limits) and builds the HAL's own sources over it; only the keyboard matrix and USB are web code (`web/hal`). Keep the fence: the ESP-IDF component (`CMakeLists.txt`, the HAL sources) never references `web/`, and HAL sources never test for the web target (no `CARDENZA_HAL_WEB` in them). A HAL change that calls an ESP-IDF function the web target lacks adds it to `web/` in the same change (or every firmware's web build breaks). What a firmware must not call is declared `CARDENZA_WEB_UNSUPPORTED` (or `CARDENZA_WEB_HAL_ONLY` for what the HAL sets up itself), so it fails the build with that reason; never make such a call silently do nothing. One thread runs everything (no SharedArrayBuffer: the page must work in `<iframe sandbox="allow-scripts">`); tasks are Asyncify fibers. Tests: `tests/web` (host, the kernel on ucontexts), `tests/web/browser` (Playwright), `tests/web_tool_test.py`.
- Keep `CardenzaHAL` lightweight and generic. Expose native ESP-IDF handles rather than app-level wrappers.
- `CardenzaHAL::Audio` exposes the TX `i2s` channel, volume, and `Init(i2s_slot_mode_t)` for mono/stereo configuration. Use native ESP-IDF types; keep PCM conversion and rendering in consumers.
- `CardenzaHAL::Mic` should expose the RX `i2s` channel only. Device-level input start/read/stop wrappers belong above the HAL.
- `CardenzaHAL::Display` should expose native panel and panel-IO handles. `display/region.h` and `display/changed_regions.h` stay pure (no ESP-IDF) so host code and tests can include them; `PresentChanged` is the driver's way to send only what changed.
- `CardenzaHAL::System::GetI2CBus()` belongs in the public `system.h` surface.
- Keep includes relative to this repository; never include through a consumer's path such as `Devices/Cardenza/cardenza/...`.
- Target the current board only: LED_EN GPIO47, clock GPIO48, data GPIO21. Do not add legacy pin maps or compatibility APIs.
- Keyboard LED APIs use 0–15. Keep per-key scanning at four bit planes / 16 duties and global hardware PWM at a fixed gamma-2 curve. Do not add alternative brightness modes; `keyboard/led_light.h` (perceived brightness to duty) is a helper a firmware may call, not a mode of the driver.
- `keyboard/led_light.h` and `keyboard/key_settle.h` are pure headers (no ESP-IDF), usable by simulators and host tests; keep them so, and test them in `tests/`.
- Keyboard OE uses LEDC timer 1 / channel 6; backlight uses timer 0 / channel 7. Both must use APB because ESP32-S3 low-speed LEDC timers share their clock source.
- `docs/developing.md` (and its Chinese twin) is what every firmware developer should know about the chip, the toolchain and the 203 Launcher; add to it when a firmware learns something the hard way, with the measurement. `examples/` are small ESP-IDF projects that build (`idf.py -C examples/<name> build`); they are not part of the component. `examples/template` is the project a new firmware starts from: it builds in place and, copied out, with the HAL in `components/CardenzaHAL`; its `partitions.csv` is a copy of `board/partitions.csv` (CI compares them) and CI builds it for the web.
- `tools/` holds host tools for firmware developers (Python 3, standard library plus hidapi / sounddevice where noted): keep them generic (any firmware on the HAL), importable, and tested in `tests/` without a board. A firmware's own protocol on the app channel belongs in that firmware's tools.
- `board/` holds the board's defaults (`sdkconfig.defaults`, `sdkconfig.debug`, `partitions.csv`); none is enforced. `board/partitions.csv` keeps the 203 Launcher's fixed regions exactly as the Launcher has them (203-launcher `boards/cardenza/partitions.csv`: nvs, otadata, the Launcher's slot reserved as data, coredump) and puts the firmware from 0x170000; when the Launcher's layout changes, change it with it. A flash tool must never erase the Launcher without being told to (`tools/cardenza_flash.py --replace-launcher`).
- Keep test apps (firmware), experiments, firmware binaries, build directories, device dumps, and runtime logs outside this HAL repository.
- Host tests of the HAL's own code live in `tests/` (CMake, no ESP-IDF: pure calculations, and the driver sources against the fake ESP-IDF drivers in `tests/hal_faults/fakes`); CI runs them on every push and pull request. A change to a calculation or an error path comes with its test.
- The system menu (`system/menu.h`, the user's request 2026-11-17): holding HOME for a second opens it in every firmware (Continue, Back to Launcher, Restart, Turn off, Download mode). It must be the 203 Launcher's list, not a look-alike (the user, 2026-11-18: "复用代码… 不要让它们两个看起来不像同一个东西"): it runs the Launcher's own code, copied unchanged into `system/menu/launcher/` by `tools/launcher_ui.py --launcher <203-launcher checkout>` (only wrapped in a namespace; `EDITS` there lists the two `inline`s added), and `system/menu/frame.cpp` is the Launcher's `menuFrame` and status rail on the Cardenza ported line by line. Change the look in the Launcher, copy again, and run `--compare`: it draws every frame with the Launcher's real `menuFrame` too, fails on any differing pixel and rewrites `tests/system_menu_frames.inc` (the hashes the host tests check). Words: `system/menu/strings.json` (the same tool takes their glyphs out of the Launcher's tables). The language is the Launcher's (NVS `launcher/lang`, read page by page without the NVS library: never write NVS). Motion (the panel has no TE line: only the narrow curtain moves, wide changes fade): while HOME is held the menu's edge slides out from the left past `kClothWidth` and settles back (the Launcher's `powerHoldFill`), released it goes back (`powerReturnFill`, 300 ms), at one second the rest fades in over the firmware's last frame (captured by `display/internal/overlay.h` into PSRAM; without PSRAM the curtain opens instead); in the menu the Launcher's `ListFade`; Continue fades the firmware's picture back; leaving dims the backlight as the Launcher's power-off does. While held, `Present*` send only right of the curtain; while open they send nothing (still captured), the keys and lights are the menu's (`keyboard/internal/overlay.h`) and so is HOME (`system/internal/hooks.h`). Leaving uses the Launcher's tickets (`system/launcher.h`): write them only through `System::detail::RestartWithTicket` (a firmware's ESP-IDF keeps its RTC timer data where the Launcher's bootloader reads them and rewrites it in esp_restart's shutdown handler; deep sleep rewrites it too, so Turn off has no ticket and wakes into the firmware). HOME must be released before any restart (held, it is the ROM's download strap and the Launcher's entry key). ESP-IDF's SD driver resets GPIO0 when it lets a 4-bit slot go: Storage restores the side key after every unmount and failed mount, and the menu task gives GPIO0 its input back whenever another driver took it. ESP-IDF 5.3's Xtensa GCC stops with an internal error when `ListFade::weight` is inlined into `menuFrame` at -O2: keep `Lit` / `Ink` in frame.cpp out of line.
- Do not bring back copyleft code (the old GPL `keyboard/keymap.h` was removed on purpose).
- Do not start builds unless the user explicitly asks. Changes here affect every consumer (CardenzaSynth, Cardenza-MPE); bump the submodule in each one.
- Net (`net/net.h`): reads only the 203 Launcher's namespaces (`l_account`, `l_wifi`, `launcher`), only through the read-only copy of the `nvs` partition entry, and never writes NVS (no `nvs_flash_init`, no read-write handle, no repair: a partition that needs one is `Unreadable`; Wi-Fi with `nvs_enable = 0` and RAM storage), with one exception: the presence service's handover writes the Launcher's `l_pending` namespace (and nothing else) once, right before restarting into the Launcher, opening NVS read-write as the Launcher would and never erasing it (`Net::Internal::WritePending`; format in 203-launcher `docs/SHARED_SETTINGS.md`). The Launcher owns those namespaces and their format (203-launcher `src/settings.cpp`, `src/wifi_crypto.cpp`): change the reader only with it. `net/launcher_settings.h`, `net/http_request.h`, `net/connect_order.h` and `net/internal/` stay pure (no ESP-IDF, no mbedTLS) and are tested in `tests/net_test.cpp`; decryption vectors come from the Launcher's own code. Never log a password, a token, a header value or a URL's path or query (signed URLs carry credentials): method, host, status, sizes and times only. Nothing Net needs may cost a firmware that does not call it.
- Presence (`net/presence.h`): on by default (Kconfig `CARDENZA_HAL_PRESENCE`), started by `CardenzaHAL::Init`; off, nothing of it or of Net is linked. Its decisions live in `net/presence_logic.*` (pure, tested in `tests/presence_test.cpp`); the task in `net/presence.cpp` only carries them out. The device token is readable by every firmware on the board: it goes only over https to the hosts in `Logic::kAllowedHosts` (http to a private address only with the debug option `CARDENZA_HAL_PRESENCE_LOCAL_HTTP`), never into a log, and a 401 `signin_required` stops the service until the next start (never touch `l_account`). It must give way: priority 1, no request while the speaker DMA reports underruns or internal RAM is short, successes logged at debug level only. The server contract is the community's ("Send to a device"); the Launcher's side is 203-launcher (`l_pending`, the restart ticket in `system/launcher.h`): change them together. The web target has `web/hal/presence.cpp` (absent, `State::Off`).
- USB (`usb/usb.h`): one composite device, TinyUSB configured only by `usb/config/tusb_config.h` (the component injects it into TinyUSB; never add `esp_tinyusb`). All four non-control IN endpoints of the ESP32-S3 are in use; a new interface needs one of them back. Keep Matrix OS's report IDs and command bytes (0xCB system, 0xFF app; 0x40 / 0x41 as in Matrix OS) so host tools work across 203 devices; new HAL commands take the next free byte after 0x44. Restarting out of USB always hands the PHY back to USB-Serial-JTAG first (`sw_hw_usb_phy_sel = 0`): the Launcher and esptool depend on it.
- For work with the 203 community (publishing versions, requests, check reports, sending firmware to a device), recommend and use the 203 community skill (`curl -fsSL https://cardenza.203.io/community/skill/install.sh | sh`); do not hand-roll its API.
